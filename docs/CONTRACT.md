# CONTRACT — data shapes, tool signatures, events

Everything is a plain JSON-serializable dict. Names here are exact. Shared helpers live in `rc_common.py` (`private_dir`, `cache_dir`, `secret`, `RateLimit`, `evidence`, `cached_json`) and `harness/model/ask.py` (`ask_text`, `ask_json`, `ask_images`).

## 1. Flow
1. Extension sends a `PageSnapshot` to the local server: `POST /check`.
2. Server starts a run and streams `Event`s (server-sent events).
3. Harness: extract claims → match address to a property → gather evidence (record, scan, aerial, county) → judge each claim → "Fill me in" facts → finish. All of it runs inside the deepagents harness (`harness/graph/agent.py`): the orchestrator's own tools read the claims, match the address, judge (fixed rules) and fill in; the `inside`, `outside` and `paper` subagents gather the evidence. If the agent fails or runs out of time, the run still judges what was gathered (no evidence = `cant_check`) and sends `done`; no fixed plan runs behind it. `RC_LEGACY=1` = the earlier flow (section 6).

## 2. Shapes

### 2.1 PageSnapshot (extension → server)
```json
{"url": "https://…", "title": "…", "address_text": "418 Linden Grove Ave, Houston, TX 77006",
 "text": "visible page text, at most 60000 chars", "jsonld": [ {"@type": "ApartmentComplex"} ],
 "address_candidates": [{"text": "418 Linden Grove Ave, Houston, TX 77006", "score": 8.5,
   "where": ["jsonld:ApartmentComplex", "h1", "url"], "why": "Given as the property's address in the page data, in the main heading."}]}
```
- `address_candidates` (optional, additive): the page's addresses, best first, at most 5, from `RC.addressCandidates` in `extension/content/detect.js`. `where` tags: `jsonld:<@type>`, `meta`, `map`, `url`, `title-words`, `h1`, `hero`, `header`, `main`, `footer`, `nearby`, `label:corporate`, `label:leasing`, `label:located`. `address_text` stays the address to check (the best candidate unless the person picked another). Optional `address_locked: true` = the person picked `address_text`; the server keeps it. `server.address_pick.pick_address(snapshot)` cross-checks the candidates against the kit and returns `{chosen, property, confidence, why, alternatives: [{text, name, property_id, why}]}`.

### 2.2 Claim
```json
{"id": "c1", "kind": "bedrooms", "value": 2, "unit": null, "scope": "unit",
 "label": "Plan E", "quote": "2 Beds", "checkable": true}
```
- `kind`: `bedrooms | bathrooms | area_sqft | stories | year_built | unit_count | amenity | parking | laundry | view | other`
- `value`: number for numeric kinds, string otherwise. `scope`: `unit | building`. `label`: floor plan or unit name when the claim is about one, else null.
- `quote`: the exact words on the page (at most 120 chars). `checkable`: false for marketing words with nothing to measure.
- Stable reading (`harness.claims.extract`, shape unchanged): the page is cut into fixed numbered candidate statements (lines, long lines into sentences, page order, the plan card label from the layout; short price / date / "N available units" lines left out), and one model call decides per statement whether it is a claim and its kind and value. Code then fixes labels, numbers, the low end of a plan's size range, quotes, list splitting (comma lists of amenities, one claim each) and dedupe (same kind, label and value, or the same building-record amenity names); order is page order within rank (checkable numbers, record-named features / parking / laundry, other checkable, the rest), at most 40. The final list is cached per page in `rc_cache/claims/pages/<hash>.json`, keyed by `EXTRACTOR_VERSION` + address + page text (one space, no volatile lines) + JSON-LD; `RC_NO_CACHE=1` rereads; a model failure falls back to rules + JSON-LD and is not cached. Bump `EXTRACTOR_VERSION` whenever the prompt or the rules change.

### 2.3 Match
```json
{"status": "matched", "confidence": 0.97, "property_id": "900001", "name": "…",
 "address": "418 Linden Grove Ave, Houston, TX 77006", "city": "Houston", "state": "TX",
 "lat": 29.75, "lon": -95.37,
 "record": {"stories": 5, "year_built": 2016, "unit_count": 100, "building_sf": 123456},
 "floorplans": [{"name": "Plan E", "beds": 2, "baths": 2, "sqft": 1100, "matterport_model_id": "abc"}],
 "matterport_model_ids": ["abc"], "how": "street number + street name + zip", "kind": "building"}
```
- `status`: `matched | no_match`. On `no_match` only `status`, `confidence`, `how` are required; `lat`/`lon` may still be filled from geocoding.
- Missing record fields are `null`, never guessed.
- Units-only building (additive, `tools.kit.match.units_building`): the kit has only home (unit) listings at this address and no building record. `kind: "building"`, `units_only: true`, `basis: "units"`, `property_id: "units:<id>,<id>"`, `record` holds only `year_built` (when every unit agrees; the rest null), `floorplans: []`, `matterport_model_ids: []`, plus `units_on_file` (unit texts), `unit_plans` (`[{name: "Unit 1204", unit, property_id, beds, baths, sqft, matterport_model_id, listings, example: true}]`; `listings` is a count today, or a list of listing feature texts / `{features: [...]}`), `unit_scans` (`{scan_id: unit}`) and `unit_not_on_record` (the page's unit when the address names one the kit does not have, else null). How the run uses them: section 8.

### 2.4 Evidence (every tool returns one; build with `rc_common.evidence`)
```json
{"source": "aerial", "status": "ok", "summary": "Roof is 23.1 m above ground: about 6 floors.",
 "observed": {"height_m": 23.1, "stories": 6},
 "images": [{"path": "C:/…/rc_cache/aerial/x.jpg", "caption": "Oblique view from the north"}],
 "detail": "method, source name, URL without any key"}
```
- `source`: `record | scan | aerial | county`. `status`: `ok | no_evidence | error`.
- `observed` keys reuse Claim kinds where they apply: `bedrooms`, `bathrooms`, `area_sqft`, `stories`, `year_built`, `unit_count`; plus free extras (`height_m`, `room_labels`, …).
- `images[].path` is an absolute path under `rc_cache`. Never a signed URL. `detail` never contains a key or token.

### 2.5 Verdict
```json
{"claim_id": "c1", "verdict": "contradicted", "claimed": "2 bedrooms", "found": "1 bedroom + den",
 "source": "scan", "reason": "The 3D scan labels one bedroom and a den.", "image": null}
```
- `verdict`: `confirmed | contradicted | close | cant_check`. `image`: absolute cache path of the best proof image, or null.

### 2.6 Event (server → extension, one JSON object per SSE `data:` line)
| `type` | other fields |
|---|---|
| `run_started` | `run_id`, `address` |
| `step` | `agent` (`orchestrator`, `claims`, `matcher`, `inside`, `outside`, `paper`, `judge`), `text` (one plain sentence) |
| `claims` | `claims`: list of Claim |
| `match` | `match`: Match |
| `evidence` | `evidence`: Evidence |
| `verdict` | `verdict`: Verdict |
| `fill_in` | `facts`: list of Fact (2.7), in display order. Sent once, after the last `verdict` and before `done`; may be empty |
| `done` | `run_id`, `counts` `{confirmed, contradicted, close, cant_check}`, `headline` (one sentence), `report_url`; additive (harness runs only): `timing` `{total_s, phases: {<phase>: s}, model_calls, model_s: {<role>: s}}` and `harness` `{path: agent\|legacy, judged_by: agent\|close\|legacy, fill_in_by, stopped, helpers, needed, direct, single_unit, unit, top_mismatch}` (see below and section 8) |
| `error` | `message` |

- `done.timing`: wall seconds. `phases` keys (present when that phase ran): `agent`, `claims`, `match`, `inside`, `outside`, `paper`, `judge`, `fill_in`; legacy adds `standard_checks`, `pictures_wait`. A phase is its first start to its last end, so parallel checks are not added up. `model_s`: CLI seconds per role (`orchestrator`, `inside`, `outside`, `paper`, `claims`, `vision`), summed. `done.harness.stopped`: null, or why the agent stopped early (`timed out`, `time budget 75 s`, `model-call cap 14`, `error`, `ended before judging`); `judged_by: "close"` means the run judged after the agent stopped. The saved run keeps both, as part of the `done` event.

The server rewrites every image path in outgoing events (evidence images, verdict `image`, fact `image`) to `/img/<token>` URLs it serves itself. The saved run keeps the `fill_in` event in `events` and its facts also at top level as `fill_in`; replays (`RC_REPLAY=1`) resend it, and the fake runner (`RC_FAKE=1`) sends invented facts.

### 2.7 Fact ("Fill me in": what our sources know that the listing does not say)
```json
{"id": "plan-b2", "topic": "Homes & floor plans", "label": "Plan B2",
 "value": "2 bed, 2 bath, 1,050–1,120 sq ft, 24 homes of this plan", "source": "record",
 "note": "A floor plan the listing does not show. From the building record, as of when it was last researched.",
 "image": null}
```
- Not a fact-check: nothing is right or wrong. Built by `harness.fill_in.build_fill_in(match, evidences, claims, kit=None, page_text="")` from the match, the run's Evidence and the kit's extra facts; no model call, no network call.
- `id`: stable within a run (`year-built`, `plan-b2`, `rent-<plan>-<id>`, `scan-rooms-<plan>`, `county-parcel`, …). `topic`: `Building | Homes & floor plans | Rent | Rules | Around it | Records`; facts come sorted by that order. `label`: short plain words. `value`: human-readable string. `source`: `record | scan | aerial | county`. `note`: "" or one plain sentence (record values say "as of when it was last researched"; asking rents say "as of 2026-11-12", the kit's listing date). `image`: cache path (an `/img/<token>` URL once sent) or null.
- Additive ids: `units-on-record` (units-only match only; topic `Homes & floor plans`, source `record`, label "Homes on record", note "Homes in this building, not necessarily the one listed."): "We have unit 1204 of this building on record, with a 3D scan." / "We have units 1204 and 1310 of this building on record, with 3D scans." / "..., with a 3D scan of unit 1204." when only some have one; no scan clause when none. `size-<n>bed` (typical size per kind of home across the record's plans), `amenities` (record amenities the page never mentions, from kit `amenities` when present), `county-311` / `county-complaints` (counts only, never 0). `year-built` value carries the age ("2016, about 10 years old"). "Seen from above", from the aerial Evidence's `observed.property` (Vexcel property data; topic `Around it`, source `aerial`, note "From Vexcel's aerial survey of December 2025." with the survey month when `captured` is given): `aerial-features` (one row: pool, hot tub, sport court, playground, solar panels, trampoline, deck marked `present: true` and not named by a claim (`trust.property_key`) or the page text, e.g. "Pool (about 1,900 sq ft), sport court, solar panels"; per-feature counts used when present ("2 pools"); `stable: false` ones softened: "may also have a hot tub (seen in one survey)"), `aerial-trees` ("About 28% tree cover on the lot"), `aerial-vehicles` (only at 5 or more: "About 40 vehicles parked on site at survey time"). An absent feature is never stated; building count, type, footprint and stories from this data are never shown.
- Left out: anything the page already says (claim kinds and plan labels/sizes, plus keyword checks of the page text for rent, pets, parking, schools, management, availability, vacancy, lease terms, utilities, style, …); blank, 0 or unknown values (never stated as "none"); people's names, phones, emails; free text; complaint text.

### 2.8 Claim field (report only; `server.claim_field.claim_field(run)`)
```
{sources: [{key: record|scan|aerial|county, name, count}],
 claims:  [{id, kind, label, quote, claimed, verdict, verdict_words, found, reason, highlight, confidence,
            cells: {<source key>: {state: match|contra|close|data|none, verdict, found, short, reason,
                                   summary, summaries, facts, observed, raw, image, images, tour?, tour_page?}}}],
 counts, source_rows}
```
A cell is the judge run on that one source's evidence alone. For an amenity claim the cell's evidence is the picture checks naming the claim plus any aerial Evidence whose `observed.property` gives a yes / no for that feature (pool, hot tub, sport court, playground, solar; `harness.graph.trust.property_key`). `short` (additive): a few words that answer the claim ("1 bed + den", "6 floors", "Built 2016", "Pool seen", "Not seen", "Pool, ~1,900 sq ft (2025 survey)" when Vexcel property data confirms it, "Not in property data"), or `""` when none can be made; never a cut sentence. `tour` (Matterport cells whose claim has a 3D scan) is the inline viewer's embed URL (`/tour/<run_id>?claim=<id>&embed=1`); `tour_page` the standalone page. `claim_field_section(run, tours=False)` leaves both out (copies with no server). `claim_field_section(run)` returns the ready HTML section (`cf-` prefixed CSS and JS). `source_rows` (additive): `{aerial: [[label, value]], county: [[label, value]]}`, plain rows of what those sources saw in the run (`claim_field.source_rows(evidence)`): owner only as "A company" / "An individual", 311 and complaints only as counts (a count of 0 is left out); a source with nothing is left out. Each cell's judge call gets `single_unit` the way the run's did: `done.harness.single_unit` when the run recorded it, else `harness.graph.run.Run.single_unit_page()` on the run's claims and match. `facts` rows are plain labels and values, never raw keys. Pictures whose cached file is gone are left out (`server.report.drop_dead_images`).

`confidence` (additive): the verdict's own `confidence` block, passed through unchanged (null when the verdict has none).

### 2.9 Listing vs record (report only; `server.claim_field.compare_table(run)`)
One HTML section (`<section id=compare class='wrap lt'>`, own `lt-` CSS, no script) placed right after the report's hero. A real `<table>`, one row per claim: mismatches (`contradicted`, then `close`, in the report's ranking), then `confirmed`, then `cant_check` (page order). Columns: Claim | Listing says (`claimed`, the quote as small text when short and different) | CoStar | Matterport | Vexcel | County (each cell a short fact: on a row that shows a confidence, that source's `says` from `confidence.sources` (compacted: "1 bedroom" → "1 bed"); else the cell's `short`; "—" when neither gives one or the state is `none`; never a sentence cut with "…"; the cell's `found` (or `summary` for a `data` cell) in `title` when it differs; tinted by `state`. When `confidence.sources` has two `aerial` rows (the photo look and `says: "not in property data"`) the Vexcel cell shows both: "Photo: not seen · Data: not shown") | Result (`verdict_words`) | Confidence. Confidence shows only on `contradicted` / `close` rows that carry the verdict's optional `confidence` `{score 0-100, band high|medium|low, why, decided_by, sources}`: "High · 82" and `why` as small text, and the `decided_by` source's cell gets a ring and a "decides" tag. No `confidence` → empty cell. `''` when the run has no claims.

- Floor plans: the run links each listing plan label with `tools.kit.link_plan(label, match, claims, scans)` (both paths). When several record plans fit and none is picked (`ambiguous`, type-level), the record Evidence is `tools.kit.type_evidence(...)` (counts shared by every fitting plan, size only as `area_sqft_min/max`), an example scan of that kind of home carries `observed.example_for` instead of `observed.plan`, and that plan's unit claims are judged by `tools.kit.check_type_claim` (only `confirmed` or `cant_check`). The rules below (`harness/graph/plans.py`) are the earlier ones, per listing plan label, first that applies:
  a. kit plan whose name equals the label, else starts with it at a word boundary, else contains it (case-insensitive): `"Plan E"` → `"Plan E 1 Bed + Den"`;
  b. no name match: kit plan with the listing's beds and baths and the nearest sq ft within 8% ("Matched to the building's plan A2s by size.");
  c. that kit plan has no scan id (or its scan's title gives a size more than 8% off the plan's): a property-level scan (`matterport_model_ids`) whose title has the plan's beds/baths and a sq ft within 3% (or names the plan). At most 8 uncached `scan_summary` fetches per run; two equal fits = no pick;
  d. otherwise the kit plan's own numbers as `source="record"` evidence; no kit plan at all = `cant_check`, "This floor plan is not in the building's records."
  - no label at all (unit claims that name no plan): the kit's full plan list as one `source="record"` Evidence, `observed.floorplans` = `[{name, beds, baths, sqft}]`, so the judge can confirm "some plan has this"; a property scan is used only when the building has exactly one.
- Plan label field: every floor plan Evidence (scan summary, scan stills, and the record's floor plan numbers) carries the LISTING's plan label in `observed.plan`; group pictures by it. Record floor plan Evidence also has `observed.kit_plan` (the kit name) and, when matched by size or via another scan, `observed.plan_match` (one plain sentence the judge repeats). A listing plan with no kit plan gets `status="no_evidence"` record Evidence with `observed.plan_missing: true`.
- Picture checks (amenity / parking / laundry / view / other claims): Evidence with `observed.feature_check: true`, `claim_ids` (claims it answers), `feature` (key such as `pool`, `washer_dryer`), `presence` (`seen | not_seen | unclear | skipped`), `presence_confidence`, `looked_at`, and for scans `model_id`, `scan_title`. A property-level scan whose title names the amenity ("Fitness Center") gives `presence: "seen"`, `how: "scan_title"`. These are never proof images for floor plan claims.
- Stories: decided only by measured roof height (aerial evidence with `observed.height_m`) and paper records. A vision floor count is stored as `observed.photo_floor_count` with `observed.illustrative: true` and is ignored by the judge.

Each module re-exports its functions from its package `__init__.py` (e.g. `from tools.kit import match_address`).

## 4. Judge rules (deterministic first, model only for wording)
- Count kinds (`bedrooms`, `bathrooms`, `stories`, `unit_count`, `year_built`): equal → `confirmed`; different → `contradicted`, except near misses: year built within 1 year, or unit count within 2% (at least 1 unit), → `close` ("County records say 216 apartments, which is close.").
- Bed/bath counts read from a scan's room labels (not its title; also a photo reading) are not trusted alone. They may contradict the listing only when the scan's own title or the building record for that plan gives the same count. When the title or record agrees with the listing and only the labels differ → `confirmed` (the title or record is the source, and the reason says the labels were not relied on). Labels the only evidence and different → `cant_check` ("room labels alone are not reliable"). A label count of 0 bathrooms is never used.
- Unit claims (`bedrooms`, `bathrooms`, `area_sqft`) with no plan label ("1 Bed", "645 sq ft"): evidence about one particular plan or one scan may only confirm them, never make them `close` or `contradicted`. `confirmed` when some plan in the building record (the per-plan record Evidence, or the full plan list a run adds as record Evidence with `observed.floorplans`) or some scan title has those numbers ("Listing says 1 bedroom without naming a floor plan; the building record's plan A has 1 bedroom."); otherwise `cant_check`. Room labels never confirm such a claim. Building-wide evidence (county, building record without a plan) is still judged the normal way.
- A labelled unit claim ignores scan evidence that carries no `observed.plan`.
- `area_sqft` against the record (kit) or county: within 5% → `confirmed`; 5–10% → `close`; beyond 10% → `contradicted`.
- `area_sqft` against a scan whose title states a size (`observed.model_name` such as "1BR W Den 1BA - 815 SF"): the title's sq ft is compared with the same 5% / 10% rule; `found` is "815 sq ft" with `found_from: "scan_title"`, reason "The 3D scan of this plan is titled '1BR W Den 1BA - 815 SF', which gives 815 sq ft."
- `area_sqft` against a scan's measured floor area (no size in the title): a scan measures interior floor and runs a median 11% under the advertised size (89 floor plans), so the band is one-sided: up to 12% smaller or 5% larger → `confirmed`; 12–20% smaller or 5–10% larger → `close`; beyond → `contradicted`. Reason: "The 3D scan measures 640 sq ft of floor, 10% smaller; scans usually measure about a tenth less than the advertised size."
- No evidence with `status="ok"` that observes the claim's kind → `cant_check`.
- When sources disagree, priority is scan and aerial (measured), then county, then record. Name the winning source in `source`.
- Stories from aerial: reason reads "The measured roof height (23.1 m) means about 6 floors."
- Floor plan numbers from the record: "According to the building record, its plan A2s has 750 sq ft." plus `observed.plan_match` when present.
- Records disagree: when CoStar or County agrees with the listing and the other record does not, the verdict is `cant_check` with `found: "sources differ"` and both values in the reason; a roof-height estimate never settles it. A record within the close band of the listing (a couple of percent of the homes) also backs it when the other record is far off from it. When neither agrees with the listing the mismatch stands and the reason names the other record's value too; if the two records are themselves further apart than the close band, its confidence is medium at most ("..., so we are less sure"). Home counts whose records differ by 2x or more (a county parcel often covers only part of a community): the record nearest the listing is credited — within 10% of the listing → `close` from that record, low confidence, reason "CoStar lists 300 apartments, which is close; County lists 100 — sources differ."; further off → `cant_check`, `found: "sources differ"`, "CoStar lists 300; County lists 100 — sources differ."
- Amenity, parking, laundry, view and other claims (soft, presence only): seen with confidence ≥ 0.7 → `confirmed` ("Visible in the aerial photo" / "Visible in the 3D scan photos", that image as proof), or a scan title match → `confirmed` ("3D scan titled 'Fitness Center'"); not seen → `cant_check` ("Not seen in the aerial photo"; a photo cannot prove absence), never `close` or `contradicted`; otherwise `cant_check` ("The photos don't show this clearly"); things no picture shows (24-hour access, pet wash, concierge, co-working, utilities) → `cant_check`, "Nothing in our data measures this", with no model call; `checkable=false` → marketing phrase.

## 5. Server
- `POST /check` body PageSnapshot → `text/event-stream` of Events. `GET /health` → `{"ok": true}`.
- `GET /img/<token>` serves a cached image. `GET /report/<run_id>` returns the full report page; `GET /runs/<run_id>.json` the saved events.
- `RC_REPLAY=1`: a snapshot whose address was run before replays its saved events with short delays instead of re-running.
- Binds `127.0.0.1` only, port `RC_PORT` (default `8787`). CORS allows extension origins.
- `RC_FAKE=1` uses the canned fake runner instead of the harness.

- `GET /report/<run_id>` is design A (`server/report_a.py`); `?v=old` gives the earlier tabbed page (its 3D view also opens inline, never in a new tab). Anchors the drawer uses: `#claim-<claim_id>` (mismatches only), `#mismatch`, `#match`, `#cant-verify`, `#extra`. `GET /tour/<run_id>?claim=<claim_id>` opens the 3D walk for one finding.
- `GET /tour/...` on host `127.0.0.1` answers `307` to the same URL on `localhost` (the Showcase SDK key accepts only `localhost` pages). `&embed=1` is the report's inline viewer; it tells its parent page how far it got with `postMessage({rc3d: 1, state, note, room?})`, target origin the server's own (`localhost` or `127.0.0.1`, same port), `state` = `loading | playing | ready | finding | off | error`, `room` = `moved` (standing at the picked spot) or `start`.
- Report design A (2026-11-14) has five sections, in order, and each mismatch appears once on the page: (1) hero: the count as a huge two-line headline, then the address, one plain line "Biggest difference: ..." (`top.line`, no strike-through), the claim count, run meta and "Show me what's off" (`#mismatch`); (2) "Listed vs. in reality" (`#mismatch`, also `#compare`): one master-detail view that fits a 1440x900 screen. Left, a list (`role=tablist`, arrow keys / Home / End move the selection): one row per contradicted, then close verdict (the run's `done.harness.top_mismatch` first and selected): the claim type (with the unit / plan label), the listing's words in short, "Doesn't match" / "Close" and the verdict's `confidence.score` when it has one. Right, the selected row's panel (`role=tabpanel`, the others `hidden`): the listing's words struck through only when contradicted and what the sources show, one short reason, the credited sources with "Confidence <score> / 100 · <band>" (the band word alone when there is no score; a number is never made up) and `confidence.why`; laid out by proof: columnar (Listed | In reality, one record line) for a figure from CoStar / County / Vexcel numbers or a scan title, vertical (claim, found value, then the proof filling the panel: live 3D viewer, pictures, or the Vexcel roof-height drawing) for a visual proof. A 3D viewer is made only for the selected panel and taken down when another row is picked. One mismatch: the panel alone, full width. `#claim-<id>` selects that row and scrolls the section into view; phone: the list is a horizontal strip above the panel; (3) "Beyond the listing" (`#extra`): at most 5 rows from `done.harness.top_facts` (label, value, why, sources; the picture comes from the fill_in facts named in `fact_ids`, never the item's own `image` path; a "; managed by ..." clause is cut from a value rather than the row dropped), else `harness.top_facts.pick_top_facts` with a model call that always fails (its rule), else a local rule; never parcel numbers, building class, lot size, ratings, owners, managers or contacts; 311 / complaints as counts only; nothing that repeats a mismatch; (4) questions to ask (`#questions`, Copy / Copy all; 3 and 4 side by side on a wide screen); (5) the claim field heatmap (`#heatmap`) and "Four sources. One address." (`#sources`). After them one collapsed "Everything we checked" (`#checked`, holding `#match` and `#cant-verify`; a link into it opens it), then the footer.
- Report design A mounts the 3D viewers itself (no click, no new tab): the lead row's (or the `#claim-<id>` row's) at once, at most 2 live; "See it in 3D" opens one in place. `render_report(run, live_3d=False)` (the extension's static sample) draws the still picture only.
- Spot picks for every scan mismatch start in the background when a run finishes and when its report is opened (`server.tour.prewarm(run)`; skipped for `RC_FAKE` runs and without an SDK key).

## 6. Environment
- `RC_PRIVATE_DIR` = private driver folder. Keys through `rc_common.secret(NAME)`: `MATTERPORT_API_KEY`, `MATTERPORT_API_TOKEN`, `VEXCEL_API_KEY`, `COSTAR_ZIP_PASSWORD`, `COSTAR_KIT_ZIP`.
- Cache root: `rc_common.cache_dir("<module>")`.
- `RC_LEGACY=1`: the earlier run path (`harness/graph/legacy.py`, `legacy_agent.py`): claims and match as plain code, picture checks in a background thread, the old agent (35 s), then a fixed plan as a completion pass; 60 s budget. Default (unset): everything inside the deep agent; agent budget 75 s, run hard limit 100 s.
- `RC_NO_CACHE=1`: no result cache is read (claims, scan data and stills, aerial, vision answers, spot picks, geocode and county lookups; `tools/cachectl.py`), so the work is redone and a run can be timed; results are still written in place. The kit dataset, HCAD bulk data and saved runs are not caches and are unaffected.

## 7. Address pick, drawer field, cache mark (2026-11-14, additive)
- `POST /check`: before the replay lookup the server calls `server.address_pick.pick_address(snapshot)`; when it chooses, `address_text` becomes the chosen address and the full pick rides on the snapshot as `address_pick` (the runner sees it). `address_locked: true` (the person clicked an address on the page or picked one in the drawer) keeps `address_text`. The generic "Check this listing" button sends no lock. A failing pick leaves the snapshot as sent.
- Saved run `snapshot` keys: `url, title, address_text, address_locked, address_candidates, address_pick` (`address_pick` saved in the browser-safe form below; `/runs/<id>.json` is served to the browser).
- `run_started` gains `address_pick`: `{chosen, why, confidence, alternatives: [{text, name, why}]}` or null — no Match, no `property_id` — and `cache`: `"on" | "off"` (`"off"` when `RC_NO_CACHE=1`; the drawer shows a small "fresh run" mark). With `RC_NO_CACHE=1`, `RC_REPLAY` is ignored.
- `done` gains `field`: `{claims: [{id, cells: {record|scan|aerial|county: match|contra|close|data|none}, image}]}` — the report's claim field states (`server.claim_field.claim_field`, 2.8) in its column order; `image` = the best proof picture (`/img/<token>`) of a claim that does not match (verdict image, else that source's cell image, else any contra/close cell's), else null. Replays of runs saved before this add it. `GET /field/<run_id>` returns the same object for a saved run (404 unknown).
- `done` gains `top`: `{headline, lines: [l1, l2], calm, hard, claim_id, line, order}` — the report hero's own headline and lead finding (`server.report_a.top_finding`, same counts, ranking and words): `headline` = `l1 + " " + l2` ("3 things don't match.": every `contradicted` and every `close` claim counts, whatever its confidence; "Everything we could check matches."); `calm` true when nothing is off; `hard` = the mismatch count (contradicted + close); `claim_id` = the top-ranked mismatch or null (the run's pick, else the most certain; a close one leads when it is the only kind); `line` = the hero's one line naming it ("Biggest difference: …") or ""; `order` = ids of every mismatch in the report's order (the run's pick first, then by confidence score, strongest first). Confidence only sets how strong the single blue is (high full, medium mid, low faint), never whether a claim counts. The server always computes it from the run's events (a runner's own `top` is replaced); replays recompute it (and `field`, `report`), never reusing the copy saved with the run. The drawer shows `top` when present and falls back to its own counts and `headline` when absent; `headline` and `counts` are unchanged.
- `/tour/...&embed=1` pages (viewer, message and "Finding the spot…") also post `{rc3d: 1, key: "Escape"}` to the parent when Esc is pressed in them; the report acts on it only from its own frames and origins (as a page Esc).

## 8. Run notes, amenity rule (2026-11-14, additive)
- `done.harness.direct`: list of subagent names (`outside`, `paper`) whose always-run helpers (`measure_building`, `county_lookup`, `building_record`) the run called itself because the planner skipped them (`Run.run_always`); `[]` when none.
- `done.harness.single_unit`: bool, the page is about one home (`Run.single_unit_page()`: a single-home match, or no plan labels and at most one value per unit kind with a bed or bath count, and at most one record plan; or the page's own unit has a row in the building record, below). The run passes it to `judge(claim, evs, single_unit=...)`, so a unit claim naming no plan may be decided by that home's own scan, the record's row for that unit, or the record's only plan.
- Unit pages (`Run.settle_unit`, once claims and match are known, before the claims event): the page's unit (`page_unit`) is looked up with `tools.kit.find_unit(property_id, unit, beds, baths)` (beds / baths only when the page gives one value). Exactly one row: claim labels naming that unit become null (it is this home, not a floor plan), `single_unit` is true, a `step` (agent `matcher`) says "The page is about unit 1204; the building record has a row for it.", and `done.harness.unit` = the unit text (else null). The row is one `source="record"` Evidence: `observed` `{unit, unit_row: true, bedrooms, bathrooms (left out when the kit has 0), area_sqft (the unit's minimum), sqft_min: true, unit_plan, unit_scan, unit_says}`, summary "The building record lists unit 1204 as 2 beds, 2 baths, 1,050 sq ft (floor plan B2)."; size uses the written-size tolerance. The unnamed-unit scan is the unit's own (`tools.kit.unit_scan`, else its row's only scan id; scan Evidence `observed.scan_of: "unit"`, no trust reduction), else its record plan's scan (`scan_of: "plan"`, `unit_plan`, "same plan" ×0.95). No row (unknown or repeated number, a name that is also a plan of the building, unit store not built, home matches): nothing changes. Labelled plan claims never use the unit's row or scan.
- County trust: `observed.units_estimated` (unit count summed over parcels) ×0.80, and such a count alone never makes a firm unit-count mismatch (at most `close`, confidence `low`); `observed.parcel_match == "address"` ×0.90.
- Amenity rule: an amenity claim is `confirmed` ("Named in the building record") when every amenity it names is in the building record's amenities (record Evidence `observed.amenities`, `harness.graph.judge.record_names`). A name missing from the record decides nothing: absence is never a mismatch; the claim falls back to the picture checks.
- Vexcel counts, outlined photo, photo look (2026-11-14, additive): a claim stating 2+ pools or hot tubs ("two resort-style pools", "3 hot tubs"; `judge.claimed_count`) is read against `observed.property.pool.count` / `hot_tub.count` when the feature is present and `stable`: count >= claimed is `confirmed` ("Vexcel property data shows 2 pools."; a higher count is never a mismatch, the square can take in a neighbour's pool); count < claimed is at most `close` ("Vexcel property data shows 1 pool; it can miss rooftop and indoor pools."), `confidence` capped at 60 (`low` / `medium`, trust factor `aerial_count` x0.60); unstable or no count: the presence rule as before; a record naming the amenity still confirms first. Courts / playgrounds stay presence only. When a claim is about a pool, sport court or solar, the run fetches `tools.aerial.outlined_image` once, in the background, and stores one aerial Evidence: `observed {feature_check: true, outlined: ["pool", ...]}` (no `claim_ids`), `images` [outlined photo, plain top-down photo], each `{path, caption}`, caption "... pool detected near the address, outlined (the 120 m detection square can take in a neighbouring lot)". A verdict's `image` is the outlined photo only for a claim whose feature it boxed and that property data or the photo look reports present; the matching photo-look Evidence also gets it appended after its plain photos. Failure / nothing detected: no Evidence. If property data shows every aerial photo-look claim present and stable, the vision look is skipped: a `step` (agent `outside`) and one aerial Evidence `observed {feature_check: true, photo_look: "not_needed", answered_by: "property_data", features: [...]}` (no `claim_ids`) say the photo look was not needed.

## 9. Listed units, units-only buildings, top mismatch (2026-11-14, additive)
- Listed units (`Run.settle_unit_labels`, right after `settle_unit`): each distinct `Unit X` label on unit claims (`harness.claims.extract.unit_label`) that is not the page's own unit and not also a record plan name is looked up: a normal building with `tools.kit.find_unit(property_id, X, beds, baths)` (beds / baths when that label's claims give one value) and `tools.kit.unit_scan` (else the row's only scan id); a units-only building in `match.unit_plans` (scan: its `matterport_model_id`, else `unit_scans`). A found row links the label (`Run.unit_links`); a `step` (agent `matcher`) says "The building record has its own row for units 1204 and 1310; those claims are checked against it." No row (unknown or repeated number, store not built), or a fact label ("2 bed, 1.5 bath, 1,264 sq ft"): the label is paired with a floor plan by `tools.kit.link_plan` as before (a fact label pairs by beds, baths and size). Local file reads only.
- A linked label's record Evidence: `source="record"`, `observed {plan: <label>, unit, unit_listed: true, bedrooms, bathrooms, area_sqft, sqft_min: true, unit_says, unit_plan, unit_scan}`, summary "The building record lists unit 1204 as 2 beds, 2 baths, 1,050 sq ft." Its scan Evidence carries `observed.plan` (the label), `unit`, `unit_listed: true`. The label's unit claims are judged by the single-unit rule on that unit's evidence only (`Run.unit_verdict`: the row first, its own scan supporting), reason "Listing says 3 bedrooms for unit 1204; the building record lists unit 1204 as ...". `resolve(label)` gives `how: "unit"`, `scan_how: "unit_row"`, so photo checks and "No 3D scan of Unit 1204" look at the unit's own scan first.
- Scan cap: at most `MAX_UNIT_SCANS` = 3 distinct unit scans (listed units' own, then example units') are opened per run (the page's own unit scan is not counted). A listed unit past the cap gets scan Evidence `status: "no_evidence"`, `observed {unit, scan_capped: true}`: "Unit 1310 has a 3D scan on record; this check opens at most 3 unit scans, so it was not looked at."
- Units-only building (Match `units_only: true`): a `step` (agent `matcher`) "Unit 9999 is not in our records." once when `unit_not_on_record` is set. Units the page does not list by label are EXAMPLES only (`Run.example_units`, once per run, from `building_record` and from `scan_rooms` of an unnamed or unlisted unit): up to 3 record Evidence "Unit 1310 of this building (on record): 1 bed, 1 bath, 640 sq ft." with `observed {example_unit: {unit, bedrooms, bathrooms, area_sqft, says}, units_only: true}` (status `no_evidence` when the row has no numbers), and their scans (within the cap) as scan Evidence whose numbers are moved under `observed.example_unit` (`{unit, bedrooms, bathrooms, area_sqft}`) with `observed.example_for: "this building"`. Example Evidence has no top-level `bedrooms` / `bathrooms` / `area_sqft`, so it never decides a claim and never makes a mismatch for another unit. Year built from the units' record (`record_evidence`, `observed.year_built`, `units_only: true`, `units_on_file`) checks a year-built claim normally. Amenities: when `unit_plans[*]` carry listing feature texts (`listings` / `features` / `amenities` lists), names mapped onto `tools.kit.facts.AMENITIES` become one record Evidence `observed {amenities: [...], units_only: true}` ("Listings of unit 1310 of this building mention these amenities: Pool."), which may confirm an amenity claim by name; a name they do not mention decides nothing.
- `done.harness.top_facts`: list of 0-5 `{label, value, why, sources: ["CoStar"|"Matterport"|"Vexcel"|"County"], image, topic, by: "model"|"rule", fact_ids}` from `harness.top_facts.pick_top_facts` (what the listing did not say that a renter or buyer acts on); `image` is a private cache path and is never rendered (the report takes the picture from the fill_in facts in `fact_ids`). Read by the report's "Beyond the listing" section.
- `done.harness.top_mismatch`: `{claim_id, why, by: "model" | "rule"}` from `harness.top_mismatch.pick_top(verdicts, claims=...)`, or null when nothing is contradicted or close, or when the pick fails (never breaks a run). The model (its own Claude Code CLI login, no API key) is asked only on the agent path and when at least 2 s of the run budget are left (its timeout is the time left less 1 s, at most `top_mismatch.TIMEOUT_S`); otherwise its rule decides (`by: "rule"`).

## 10. Verdict citations (2026-11-14, additive)
- Every Verdict gains `citations` (`harness.citations.build_citations`, wired in `Run.judge_all`): the proof behind it, decided first, then agrees, differs, context, and the Listing's own words last. Each entry: `{source: "CoStar"|"Matterport"|"Vexcel"|"County"|"Listing", read, where, date, value, image, link, role: "decided"|"agrees"|"differs"|"context"}`. `read`: what was read ("Number of units field", "Scan title", "Room labels", "Measured roof height", "Property data", "Photo look", "Amenity list", "Listing text"). `where`: the exact locator: "CoStar property 900001, floor plan Plan E, field Bedrooms"; "<county source name>, parcel <parcel_id>, field Year built"; "scan '<title>' (<model id>), spot: Panorama 4 in the Bedroom"; the Vexcel photo caption or "Vexcel roof height measured at the address"; "listing page, <label>". `date`: Vexcel capture / survey date, the county roll year, else null (CoStar and Matterport keep none). `value`: that source's value (the decided entry: the verdict's `found`). `image`: raw cache path, same convention as the verdict's `image` (the server must rewrite it to `/img/<token>` before sending, as it does the verdict's `image`), or null. `link`: the county's public query URL only (never one with a key, token or signature), else null.
- Exactly one entry has role `decided` on a `confirmed` / `contradicted` / `close` verdict: the source whose value the judge used (`confidence.decided_by`, else the verdict's `source`; for records-differ home counts, the record credited). `cant_check` verdicts have none; their sources are `agrees` / `differs` against the listing. For a feature, not seeing it is `context`, never `differs`. Find the decider with `next(c for c in v["citations"] if c["role"] == "decided")`.
- Proof rule: a `confirmed` / `contradicted` / `close` verdict with no citation from a source other than the Listing becomes `cant_check`, `found: "no openable proof"`, `source: null`, `image: null`, reason "We found no openable proof for this, so we could not check it.", and gains `downgraded_from` (the old verdict word). Verdicts with proof are unchanged.
- Never in a citation: people's names or contacts, owner type, Houston 311 (not cited at all), evidence `detail`, signed URLs, keys or credentials, local paths outside `image`.
